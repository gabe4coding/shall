# Review

A review has four steps. Each step has one owner:

1. **Select (Jev).** Jev finds the rules that apply to each file of the change. It gives a
   probability for each rule.
2. **Review (Claude, no tools).** The reviewer agent sees one file and only the rules that apply to
   it. It returns the violations as JSON.
3. **Validate (code).** Code removes findings on lines that the change did not touch, findings for
   rules that Jev did not select, and duplicates.
4. **Verify (code, Jev and an agent).** Code collects evidence from the repository for each blocking
   finding. A verifier agent answers *confirmed*, *refuted* or *unknown*. A finding blocks only if
   its evidence was seen.

[Architecture](./architecture.mdx) tells how each step works.

## Find the rules that apply

Before you start a task, ask which rules apply to it:

```bash
shall select --text "add a Kafka consumer for booking events"
shall show JRFC-0006.1
```

You can also give a diff or a file:

```bash
shall select /tmp/pr.diff
```

`shall select` uses only Jev. It takes approximately 2 seconds. With the plugin, Claude Code does this
step without a request (skill `shall-standards`).

## Review a change

Make a diff and review it from the root of your repository. The verification step searches for
evidence there.

```bash
git diff origin/main...HEAD > /tmp/pr.diff
shall review /tmp/pr.diff --out-dir .shall-out/pr
cat .shall-out/pr/review.md
```

For a pull request on GitHub, use `gh pr diff 123 > /tmp/pr.diff`.

You can also review a spec, a document or a code file. shall uses Jev to identify a Markdown file as
a spec or a document. To set the kind, use `--kind spec` or `--kind doc`:

```bash
shall review docs/design/refunds.md --kind spec
```

To post the review on a pull request, read [CI](./ci.mdx).

## Organisation rules and local rules

### Only the rules of your organisation

Set `SHALL_EXTENDS` to the corpus of your organisation, pinned to a tag or a commit:

```bash
export SHALL_EXTENDS=your-org/engineering-standards@v2026.09   # owner/name@ref, or a local path
export SHALL_GIT_TOKEN=...                                      # only for a private repository
```

To try shall with the example corpus of this repository, use `SHALL_EXTENDS=gabe4coding/shall@main`.

### Rules for one repository

A repository can add its own rules on top of the rules of the organisation:

```bash
shall init --prefix BOOK --repo your-org/engineering-standards --ref v2026.09
shall fetch                                     # download the pinned corpus into ~/.cache/shall
shall new --domain api --title "Booking events carry a schema version"
$EDITOR .shall/rfcs/BOOK-0001-*.md              # write the rule
shall lint && shall build                        # check the file, write .shall/index/ again
shall conflicts --local                         # compare your rules with the rules of the organisation
git add .shall && git commit -m "Add BOOK-0001"
```

These rules apply to local rules:

- Local rules use their own prefix, for example `BOOK-`.
- Local rules can only **add** requirements or make the requirements of the organisation
  **stricter**. `shall conflicts --local` fails when a local rule repeats, weakens or contradicts an
  organisation rule.
- There are no local waivers. If a rule of the organisation must not apply to your repository, ask
  the owner of the rule to change it in the organisation corpus.
- To get new organisation rules, change `extends.ref` in `.shall/shall.yaml`. Then run
  `shall fetch --update`.

[`examples/booking-service/.shall/`](../examples/booking-service/.shall/) is a full example.
[Standards](./standards.mdx) tells how to write a rule.

## Review inside a Claude Code session

With the plugin, ask Claude: *"check this PR against our standards"*. The skill `shall-review` runs
`shall review`. If you want to discuss the findings, the skill can also run the steps one at a time:
`shall select`, `shall bundle`, the `shall-reviewer` agent for each file, `shall validate` and
`shall verify`. Both ways use the same reviewer prompt
(`plugins/shall/agents/shall-reviewer.md`).

## Outputs

`shall review --out-dir DIR` writes these files:

| File | Content |
| --- | --- |
| `review.md` | The summary for people: findings, the rules that apply, a health line |
| `findings.json` | The validated findings, and the findings that code removed, each with the reason |
| `selection.json` | The probability of each rule for each part of a file, and the known effects |
| `github-review.json` | The payload for `shall publish` (`--format github`) |
| `health.json` | Problems that can stay hidden: failed calls, blocking findings without verification, files that shall did not parse, rules just below the threshold |
| `prompts/` | The exact prompt that shall sent to the reviewer for each part of a file |

## Exit codes

All `shall` commands use the same exit codes:

| Code | Meaning |
| --- | --- |
| 0 | Done. There is no blocking finding, or `--fail-on-blocking` is not set. |
| 1 | Error: configuration, tooling, or a failed review call |
| 2 | Blocking findings: a verified violation of a MUST rule in an `enforced` standard |
| 3 | The Jev service failed after retries. Run the job again. This is not a problem in the code. |

## Severity

The corpus sets the severity, not the reviewer:

| Status of the standard | MUST rule | SHOULD or MAY rule |
| --- | --- | --- |
| `enforced` | Blocking | Advisory comment |
| `approved` | Advisory comment | Advisory comment |
| `draft` | Not used in reviews | Not used in reviews |

To include drafts in a review, use `--include-draft`.
