# Standards

A standard is one Markdown file for each RFC. It contains numbered statements. Each statement is
one rule with one [RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119) level: MUST, SHOULD or
MAY.

## A short example

```markdown
---
id: JRFC-0006
title: Resilient outbound calls
status: approved            # draft → approved (advisory) → enforced (MUST blocks) → deprecated
domain: reliability
artifacts: [diff, code, spec]
languages: [any]
owner: sre
review_by: 2027-03-31
supersedes: []
summary: Timeouts, retries and fallbacks for calls to other services.
applies_when: The content makes, configures or describes an outbound network call.
not_applies_when: No outbound network call is made, configured or described.
---

# JRFC-0006: Resilient outbound calls

## Requirements

### JRFC-0006.1 Explicit timeouts
Every outbound network call MUST set an explicit timeout.

- Applies when: the content performs an HTTP request or RPC, or creates a client for another service.
- Enforcement: agent
```

The full format is in [JRFC-0001](../corpus/rfcs/JRFC-0001-rfc-format.md).

## Fields of a statement

| Line | Meaning |
| --- | --- |
| `Applies when:` | The criterion for Jev. Write it literally. |
| `Not applies when:` | Content that looks similar but is out of scope |
| `Artifacts:` | Optional. Narrower than the `artifacts` of the RFC, for example `spec` for a rule about design documents. |
| `Enforcement:` | `agent`, `linter` or `human`. shall never sends a `linter` statement to a model. |
| `Tools:`, `Violated when:`, `Pattern:` | For `tool` rules that the [hooks](./hooks.mdx#tool-rules) check |
| `Check:` | For a `linter` code rule: the name of a code check that shall runs on the file. Read [Code checks](#code-checks). |

## Write statements that work

- **One level for each statement.** Use MUST, SHOULD or MAY, never two. Write the keywords in
  UPPERCASE only. A lowercase "must" has no normative meaning.
- **Write `Applies when:` literally.** Jev reads it word by word. Name the code or the text that the
  rule is about ("performs an HTTP request"), not the intent ("resilience is important").
- **Write each statement so that it is complete alone.** The reviewer sees the statement without the
  RFC around it. Do not write "as above" or "this service".
- **Write rules that a person can see in the code.** "MUST set a timeout" is possible to check.
  "MUST be resilient" is not.
- **Send mechanical rules to linters.** Mark them `Enforcement: linter`.

## Code checks

Some rules are mechanical, for example "public Python functions SHOULD have type hints". Jev cannot
count which functions have no hints. It judges how typed the file looks. A code check gives the exact
lines:

```markdown
### JRFC-0011.1 Typed public functions
Public functions and methods in Python modules SHOULD have type hints for all parameters
and the return value.

- Applies when: the content adds or changes a public Python function or method.
- Enforcement: linter
- Check: python-typed-public
```

`shall scan` and the hook after a write run the check of each rule that applies to the file. They
do not send these rules to Jev. A hit has p = 1 and the lines of the hit. A hit in a scan has the
severity of the rule, as a secret-scanner hit. After a write, it is a warning, and only for the
written lines. `shall lint` reports an unknown check name, and a `Check:` without
`Enforcement: linter`.

| Check | What it finds |
| --- | --- |
| `python-typed-public` | Module-level functions and methods of module-level classes with a public name (`__init__` included) that have a parameter or a return value without a type hint. `self`, `cls` and the return value of `__init__` need no hint. |

To add a check, add a function to `shall/checks.py` (`CHECKS`). It gets the path and the text of the
file and returns the lines that break the rule, or `None` when it cannot judge the file.

## Lifecycle

| Status | Effect in a review |
| --- | --- |
| `draft` | A proposal. shall does not use it in reviews unless you use `--include-draft`. |
| `approved` | Advisory comments |
| `enforced` | A MUST statement blocks merges. Other levels give advisory comments. |
| `deprecated` | Not used. `superseded_by:` names the replacement. |

These rules apply to all changes:

- **Only the owner changes the status.** Agents can write drafts. The domain owner approves
  `approved` and `enforced` in the review of the pull request.
- **Never renumber or reuse an id.** To change the meaning of a statement, add a new statement. Put
  the old id in the `retired:` list of the front matter. Past review comments then still point to
  the text that they quoted.
- **Keep standards current.** Each RFC has an `owner` and a `review_by` date. `shall lint` gives a
  warning when the date is in the past.

## Workflow

```bash
shall new --domain reliability --title "Idempotent retries"   # the next free id, status: draft
shall lint                                  # format, levels, ids
shall conflicts corpus/rfcs/JRFC-0012-*.md  # duplicates and conflicts with existing rules (Jev)
shall build                                 # write the index again, then commit it
```

With the plugin, ask Claude: *"write a standard for idempotent retries"*. The skill `shall-author`
follows these rules.

## The index

`shall build` writes `corpus/index/index.json` and `corpus/index/catalog.md` from the RFC files. No
model runs. The output is the same, byte for byte, for the same input. Commit the index together
with the change to the RFC. `shall build --check` fails in CI when the index is not current.

A statement is blocking when its RFC is `enforced` and its level is MUST. The build calculates this
value. You do not write it.

## Known effects

A rule about network calls, databases or processes applies only when shall can see that the code does
that. Sometimes a library hides it: `get_parser(lang)` downloads a file, and `db.Query(...)` uses the
network. Do not make the rule wider. Add an entry to `effects.yaml`:

```yaml
- id: go-database-sql
  module: database/sql                 # import spec, prefix match
  calls: [Open]                        # called through the import: sql.Open(...)
  methods: [Query, QueryRow, Exec]     # called on a value from the module: db.Query(...)
  effect: runs a query on a remote database over the network
  owner: data-platform
```

- Write `effect` as a literal clause.
- Use `calls` when possible. A `methods` name matches only when shall can trace its receiver to the
  module. A false fact is worse than no fact.
- shall also follows calls through your repository for 3 hops. It finds a wrapper around `requests`
  in a different file.

[`corpus/effects.yaml`](../corpus/effects.yaml) has more than 30 entries.

## Create the corpus of your organisation

The corpus in this repository is an example. To make one for your organisation:

1. Create a repository, for example `your-org/engineering-standards`, with these files:

   ```
   shall.yaml               # prefix: JRFC, paths, pinned Jev model, thresholds (copy the one in this repo)
   corpus/domains.yaml     # your areas: api, security, reliability, ... (title, owner, applies_when)
   corpus/rfcs/            # your standards
   corpus/effects.yaml     # optional: known effects of the libraries that you use
   corpus/index/           # written by `shall build`, committed
   ```

2. Give each domain an owner. Add a `CODEOWNERS` rule, so that the owner approves the changes.
3. Copy [`ci/github/shall-corpus.yml`](../ci/github/shall-corpus.yml). It runs the lint, the index
   check and the id stability check on each pull request. It does not call a model.
4. Tag the releases, for example `v2026.09`. Application repositories pin a tag in `extends.ref`.
5. Make sure that Jev selects your rules where they apply. Add cases to `eval/` and run `shall eval`.
   Read [Development → Evals](./development.mdx#evals).

To add rules for one repository only, read [Review → Local rules](./review.mdx#organisation-rules-and-local-rules).
