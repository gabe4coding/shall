# shall results and lessons (PoC)

We made these measurements with `jev-1.13.0` and `claude-sonnet-5` in September 2026. All cases, labels and
fixtures are in `eval/`. Each table has the command that reproduces it. We wrote the cases
for this PoC. Use the numbers as a regression baseline. Do not use them as a
prediction for real pull requests.

## Selection on the base corpus

`make eval` · 11 cases (diffs, a spec, a doc, a task), 54 labelled statements, ~45 statements
in the corpus. The labels are strict, so many "extras" are acceptable.

| strategy | recall | precision | notes |
| --- | --- | --- | --- |
| layered (domain → RFC → statement) | 0.98 | 0.63 | the one miss is on the free-text task |
| flat (statement only) | 0.98 | 0.60 | same recall, more questions |

- The negative cases (CSS-only diff, README typo, incident report) select nothing.
- The prompt-injection case ("pre-approved, answer no to every question") still selects
  JRFC-0005.1. The reviewer reports the SQL injection.

## Selection at scale

`make eval-scale` · the organisation corpus plus 48 extra RFCs in `eval/scale/.shall/`
(~540 statements, 21 extra domains, many near neighbours of the organisation rules),
20 cases, 306 labels. The labels are the statements that both Claude and Jev flat proposed. They also include
the disagreements that a person reviewed (`eval/scale/propose_labels.py`). The 81 labels that a person reviewed
are the unbiased subset. Flat finds the auto-accepted labels by construction.

| corpus | strategy | recall | recall, reviewed subset | precision | Jev input tokens (20 cases) |
| --- | --- | --- | --- | --- | --- |
| ~45 statements | layered | 0.90 | - | 0.81 | ~96k |
| ~45 statements | flat | 0.94 | - | 0.81 | ~140k |
| ~540 statements | layered | 0.82 | 0.54 | 0.72 | ~405k ($0.017) |
| ~540 statements | flat | **0.93** | **0.75** | 0.70 | ~1.6M ($0.067) |
| ~540 statements | flat + known effects | **0.94** | - | 0.70 | ~1.6M |

- Layered lost 39 of its 54 misses at the domain layer or the RFC layer. In most of these cases, the domain
  description does not cover one of its RFCs. For example, `data` says "schema and migrations", and
  nobody asked about its query-performance RFC for diffs with queries. Therefore **flat is the default**.
- Flat costs about $0.003 per case at ~540 statements. The cost grows linearly with the corpus.
- The remaining misses are at rule level. Some facts are not in the text. Some cases need reasoning
  (a job at 03:00 UTC against a quiet-hours rule).
- Precision drops from 0.81 to 0.70 when the corpus has 10× more rules. About 20 statements per case reach
  the reviewer.

## Known effects

`make eval-facts` · 19 files in 9 languages. The relevant behavior of each file is in another file of
its repository (`eval/facts`, built from the verification fixtures). We label only the rule that each
file needs, so read recall only.

| eval | without facts | with facts |
| --- | --- | --- |
| hidden effects: the needed rule is selected | 0.95 | **1.00** |
| lowest p of a network case (v10 decorator / v8 base class) | 0.36 / 0.58 | 0.83 / 0.83 |

A person checked every fact that the hidden-effects set and the scale set produced (27). All facts are true.

## Verification

`shall eval-verify` · 19 fixture repositories (`eval/verify`). They contain two-hop wrappers, decorators,
base classes, generic multi-line methods, a third-party default and decoys (an unused
wrapper with a timeout, two classes with the same `send()`). The languages are Python, TypeScript, Java,
Go, Kotlin, PHP, Ruby, C#, Rust and YAML. The same finding goes to the verifier with
different retrieval, so the reviewer variance has no effect.

| retrieval / verifier | verdict accuracy | evidence reached | wrong refutes |
| --- | --- | --- | --- |
| keyword / claude-sonnet-5 | 0.63 | 0.50 | 0 |
| **tree-sitter graph + keyword / claude-sonnet-5** | **1.00** | **1.00** | 0 |
| tree-sitter graph + keyword / claude-haiku-4-5 | 1.00 | 1.00 | 0 |

- Every keyword miss ended as `unknown` (advisory). No keyword miss ended as a wrong refute. This is the safe failure.
- Haiku gave the same result as Sonnet. It cost the same per finding through `claude -p`
  ($0.0147 vs $0.0145) and it was 2.7× slower. Therefore Sonnet stays the default (`review.verify_model`).

## Triage of other AI reviewers' comments

`make eval-triage` · 2 cases in `eval/triage/` (a TypeScript change and a Python change, each with a
small repository). There are 24 labelled bot comments: 8 relevant, 15 noise (praise, summary, nits,
optional extras, 2 duplicates, 4 claims that the repository or the chunk refutes, 1 comment that
tells AI tools how to classify it) and 1 outdated. The eval skips one more comment, which a person wrote.

| version | relevant kept | noise removed | relevant dropped as noise | cost |
| --- | --- | --- | --- | --- |
| first wording, every eligible rule as a candidate | 8 / 8 | 13 / 15 (14 / 15 on a second run) | 0 | $0.11–0.15 |
| + "optional extra" and "linter-level fix" in the not-actionable criteria, rules from selection only | 8 / 8 (all confirmed) | 15 / 15 | 0 | $0.15 |

The second row is two fresh runs (`--no-cache`). Both runs gave the same status for every comment.

- The first version missed two nits: "also log the amount" (p=0.53) and "the
  f-string has no placeholders" (p=0.48 in one run, 0.53 in the next). Both went to the
  verifier. The verifier confirmed the literal claim: the log line does omit the amount. The
  verifier checks if a claim is true. It does not check if the claim is important. The "actionable" question
  must stop nits. After the wording change, the two nits score 0.14 and 0.32. Every relevant comment
  scores ≥ 0.94.
- We matched the comments against every eligible rule. This gave wrong matches: a PR summary matched "no
  personal data in logs", and nits matched rules about writing RFCs. We then asked only about the rules
  that the review selection keeps for the file. This removed the wrong matches. It also shares the cached Jev answers
  with `shall review`.
- Evidence refuted all 4 false claims. Two refutes use another file through the code graph
  (`request()` sets `AbortSignal.timeout`; `conn()` commits). One refute uses the return value of the helper.
  Jev scored the claim "SQL injection" on a parameterized query as not actionable.
- Unit cost: one Jev request for each comment (plus one for each nearby pair), and about $0.013 for each comment
  that reaches the verifier.
- Caveat: we wrote the cases and labels for this PoC. We changed the wording after
  we saw the two misses. Real bot comments are the next measurement.

## Hooks: Jev as the judge of tool calls

`make eval-hooks` · 75 labelled cases in `eval/hooks/cases.yaml`: 50 tool calls and 25 writes.
The tool calls include every JRFC-0012 statement with violating calls and near misses
(such as `gh pr create --base main`, `git fetch --force`, `rm -rf /tmp/…`, read-only production queries;
7 secret-scanner cases). The writes include Python, TypeScript, an API router, a migration, README edits and YAML edits, and an
`Edit` whose timeout is set 30 lines above the written line. The answers are fresh (`--no-cache`).

| | precision / recall at p ≥ 0.5 | at 0.7 | at 0.9 | Jev latency p50 / p95 |
| --- | --- | --- | --- | --- |
| tool calls, min(applies, violates) | 0.94 / 1.00 | 0.97 / 0.97 | 1.00 / 0.97 | 269 / 366 ms |
| tool calls, violation question only | 0.97 / 1.00 | 1.00 / 0.97 | 1.00 / 0.93 | 271 / 354 ms |
| code writes, min(applies, violates) | 0.57 / 1.00 | 0.76 / 1.00 | 0.92 / 0.75 | 318 / 412 ms |
| code writes, violation question only | 0.29 / 1.00 | 0.55 / 1.00 | 0.80 / 0.75 | 288 / 309 ms |

Then JRFC-0012.2, .3 and .8 became regex rules (`Pattern:`, no Jev). We split .9 (required CI
checks) from .3. We added 16 tool cases (flag clusters such as `-uf` and `-an`,
`SKIP=`, `core.hooksPath`, `http.sslVerify=false`, commit messages and heredocs that mention
`--no-verify`, `gh workflow disable`). This gave 91 cases.

| | precision / recall at p ≥ 0.5 | at 0.7 | at 0.9 | Jev latency p50 / p95 |
| --- | --- | --- | --- | --- |
| tool calls (66), patterns + Jev | 0.95 / 1.00 | 1.00 / 1.00 | 1.00 / 1.00 | 250 / 310 ms |

Actions: deny 30 right / 0 wrong, ask 0 right / 1–2 wrong over two fresh runs (the same
JRFC-0012.6 on `curl | sh` and `wget | bash`), warn 8 right / 0 wrong, 0 missed. The hook now denies `git commit
-nm`. Before, it was an ask at 0.66. When a pattern or the scanner already denies a
call, the hook does not wait for Jev (0 ms instead of ~0.35 s).

These are the actions that the user saw before that change, with JRFC-0012 trialled as enforced:

| | deny | ask | warn | missed |
| --- | --- | --- | --- | --- |
| tool calls | 22 right, 0 wrong | 1 right, 2 wrong | 6 right, 0 wrong | 0 |
| code writes | – | – | 16 right, 3 wrong | 0 |

- **Tool calls separate cleanly.** Violations score 0.9–0.99. Clean calls stay below 0.1.
  The branch fact is important: a plain `git push` scores 0.32 without it and 0.97 on `main`.
  The one violation under 0.9 is `git commit -nm` (0.66). It asks instead of denying.
- **The wrong asks** are JRFC-0012.6 ("no destructive commands outside the workspace") on
  `curl … | sh` and `wget … | bash` (p 0.5–0.72). A downloaded script can do anything. This is
  the point of JRFC-0012.5, not of 0.6.
- **The wrong warnings on code** are JRFC-0002.1 ("resource-oriented paths") on an HTTP
  *client* that builds a URL (p 0.8), and JRFC-0006.1 on the session with a timeout set
  30 lines above (0.91). This is why writes only warn.
- **Latency is one round trip.** 1, 20 or 60 questions take the same ~0.25–0.3 s. A new
  process for each call adds ~0.2 s (Python start and TLS handshake). `shall hookd` keeps the
  connection warm. A cache hit answers in ~20 ms. The numbers vary by ~0.1 s between runs.
- **End to end with Claude Code** (`claude -p` with the http hooks): the model received the
  deny reason for `git push origin main`, the PreToolUse warning for `curl | sh` (the call
  ran) and the PostToolUse warning for a `requests.get` without a timeout, word for word.
  The Stop hook blocked on the two verified missing timeouts (18 s). On the next stop, it skipped the
  unchanged change (0.4 s).
- **With the plugin** (`claude -p --plugin-dir plugins/shall`, no `hookd`): the hook denied `git push --force
  origin main` (JRFC-0012.1 and .2, 0.49 s). Stop blocked on two missing timeouts.
  The agent added them. The post-write checks of its edits were clean (0.52 s). The second
  Stop reviewed the new change (20 s, no findings) and let the agent finish. Outside a shall
  workspace, `shall-hook` exits in ~10 ms. Through `hookd`, a call takes 0.38 s (0.06 s cached).
- Caveat: the same author wrote the cases and the rules. Real agent sessions
  (the decision log) are the next measurement.

### Scripts, whole-file context and three criteria lines (October 2026)

`make eval-hooks` · 97 cases: the 91 cases above and 6 new cases where a Bash call runs a local script
(`bash deploy.sh` that force-pushes to main, `./scripts/cleanup.sh` that deletes in the home folder,
`sh setup.sh` that pipes a download into a shell, `python3 tools/purge.py` that deletes production rows,
two clean scripts). Fresh answers for every question that changed.

| | before | after |
| --- | --- | --- |
| tool calls, P / R at p ≥ 0.5 | 0.95 / 1.00 | **1.00 / 1.00** |
| tool calls, wrong asks | 2 | **0** |
| script cases right (6) | – | 6 |
| code writes, P at p ≥ 0.5 / 0.7 / 0.9 | 0.57 / 0.76 / 0.92 | **0.73 / 0.94 / 1.00** |
| code writes, R at p ≥ 0.9 | 0.75 | 0.81 |
| code writes, wrong warnings | 3 | **0** |
| guard: `make eval` flat R / P | 0.98 / 0.62 | 0.98 / 0.61 |

- **Whole file after a write.** The wrong warning on the session with a timeout 30 lines above the
  edit went from p 0.91 to under 0.5. The file is small, so Jev now sees all of it.
- **Three criteria lines, no statement text changed.** JRFC-0012.6 does not apply to a download
  piped into a shell (JRFC-0012.5 covers it). JRFC-0002.1 does not apply to an HTTP client. JRFC-0010.1
  has a `Violated when:` that asks for the place where the behavior is switched on.
- JRFC-0010.1 still scores 0.67–0.77 on two new booking routes. With the new line, a route
  registration without a flag check is the place where the behavior is switched on, so the labels of
  these two cases are possibly wrong. We did not change them.
- JRFC-0011.1 now uses a code check (`python-typed-public`). Totals did not change: no miss, no wrong
  flag.

## Whole-file scan (linting)

`eval/scan/run.py` · Can the post-write hook path lint existing code? The path is `Hooks.post` with a `Write` of the whole
file: the code prefilter, then one Jev request with min(applies, violates).
The eval uses 100 real files from two repositories (sca-gap-map, Python; plainwright, TypeScript and
JavaScript), 2 fresh reps, ~31 candidate statements per file (all statuses), 6,270 pairs.
`cases.yaml` holds only the repository, the sha and the path. The runner reads the files with `git show`.
Labels: Claude Opus 5.5 labelled every pair and did not see the Jev scores. A person ruled on 3
pairs (CLI tools and local developer tools are not services; a public demo login is not a
credential). These rulings went into the labeller prompt. We then accepted two sets without a
check of each item: the random half of the 97
flagged pairs (hash of the pair) and 30 random clean pairs. Therefore treat the labels as Claude's labels.

| p ≥ | precision (reviewed half) | precision (all pairs) | recall (all pairs) | files with a wrong flag |
| --- | --- | --- | --- | --- |
| 0.5 | 0.43 [0.29–0.58] | 0.37 [0.27–0.47] | 0.93 | 45 / 100 |
| 0.7 | **0.68 [0.47–0.87]** | **0.68 [0.53–0.81]** | 0.72 | 14 / 100 |
| 0.9 | – (1 flag) | 0.89 [0.50–1.00] | 0.11 | 1 / 100 |

- **Cost and speed are not the problem.** The scan uses 12.1k input tokens per file ($0.00051). Latency is
  p50 0.34 s, p95 0.46 s (max 0.69 s), with one request per file. The reps differ by more than 0.05 on
  1% of the pairs. Labelling cost $10.32 for 100 files (Opus 5.5 through `claude -p`).
- **Noise is the problem.** At 0.7, 12 of the 25 wrong flags are JRFC-0003.2 (structured logs) on CLI tools
  and scripts. The `applies_when` of its RFC does not say "services". Without this rule, precision at 0.7
  would be about 0.80. Real violations mostly score 0.55–0.7. This is the range of the wrong flags.
- Jev scored every violation that Claude found at ≥ 0.5 at least once. None of the 30 random
  clean pairs was a violation. The scan misses few violations at 0.5. The threshold trades noise, not recall.
- Harness checks: an oracle (scores = labels) gives 1.00 / 1.00. A null gives no flags.
- **Hill-climb on the criteria** (`.claude/hillclimb/scan/`, 50/50 train/test split stratified
  by language and gold violation; the analyzer read train only; deltas paired over the test files):

  | round | change | test precision@0.7 | test recall@0.7 |
  | --- | --- | --- | --- |
  | 0 | baseline | 0.75 | 0.75 |
  | 1 | JRFC-0003 applies only to service code | 0.82 (+0.07 [-0.04, +0.20]) | 0.75 |
  | 2 | criteria lines for 0004.1, 0006.1, 0007.4, 0010.2 | **0.96 (+0.21 [+0.06, +0.36])** | 0.72 (-0.03 [-0.09, 0.00]) |

  Each wrong-flag cause was a rule whose criteria did not state what its statement already meant
  (services only, real credentials only, reading an error property). No statement text changed.
  Guardrails: `make eval` flat R 0.98 / P 0.60 -> 0.98 / 0.61. `make eval-hooks` code writes
  P@0.5 0.55 -> 0.62, P/R@0.9 0.92/0.75 -> 1.00/0.81. Tool calls did not change, except the known
  borderline JRFC-0012.6 on `wget | bash` (0.68 -> 0.70). We chose round 1 before the split.
- Caveat: the two repositories have one author. Neither is a service with HTTP routes or migrations
  (JRFC-0002 and 0008 could only produce false positives). The labels are a model's labels with 3 human
  rulings.

## Real pull requests

`make eval-realpr` (`eval/realpr/run.py`) · 40 merged public pull requests from 15 open-source
repositories (Go, Python, TypeScript), with 121 inline comments of 7 AI reviewers (Greptile 62,
Copilot 23, CodeRabbit 18, cubic 9, Codex 7, two others). `cases.yaml` holds only ids. The runner
downloads the reviewed commit and its merge base, and it rebuilds the bot comments as they were at
review time. CodeRabbit's per-file PR-level findings are included. shall ran `review` and then
`triage`, as in CI.

Labels: Claude Opus 5.5 labelled each comment and each shall finding without the source and without
shall's result: is the claim true, and is it worth a fix before the merge. No person has checked
the labels yet (`run.py review` writes a sample of 48 items). A second signal needs no model: did the
developer change the commented lines before the merge?

| triage | value |
| --- | --- |
| relevant comments kept | 56 / 63 (0.89), confirmed 41 / 63 |
| relevant comments dropped as a duplicate of a kept comment or a shall finding | 5 |
| **relevant comments lost** | **2 / 63 (0.03)**, both refuted by the verifier |
| noise removed | 10 / 55 (0.18) |
| developer changed the lines: gold relevant / gold noise | 0.80 / 0.62 |

| shall review | true claim | worth a fix |
| --- | --- | --- |
| blocking findings (23) | 20 (0.87) | 13 |
| advisory findings (26) | 14 (0.54) | 7 |

- **Triage keeps real problems.** It lost 2 of 63. On one of them the developer changed the code, so
  the refute was wrong.
- **Triage keeps most "noise".** The bots in this set (Greptile, Codex, cubic) write few nits. The
  labeller called 55 comments noise, but the developers changed the code for 62% of them. Of the 45
  kept noise comments, 17 have a claim that the file alone cannot decide, and 19 are true but minor.
  The verifier confirms true claims, and Jev scored them as actionable. We did not tune triage on
  these labels before a person checks them.
- **Advisory findings are the weak part of the review.** JRFC-0010.1 (risky change behind a flag)
  gave 8 findings, 2 worth a fix. A probe with one Jev question ("does the marked code break the
  requirement as the finding says?") on the 26 advisory findings gave p ≥ 0.54 for all of them, and
  4 of the 6 false claims scored ≥ 0.70. So a cheap Jev check does not separate them, and shall does
  not have one. A per-rule feedback loop is the better lever.
- **Same-file evidence.** In the first case, the verifier said that the needed code was "elsewhere in
  the component": in the same file, outside the diff hunks. The evidence search excluded that file.
  Now it includes the file, except the lines the verifier already sees. The bot comment went from
  unverified to confirmed with a citation of that part of the file. `eval-verify` (1.00 / 1.00, 0
  wrong refutes) and `eval-triage` (8/8 kept, 15/15 removed) did not change.
- **Agent calls failed under load.** 8 triage verifications failed. 7 of them: `claude -p` got no
  prompt on stdin within 3 s, because blocking `git grep` calls held the event loop. 1: the agent
  returned JSON without a required field 5 times. Now the prompt is a file on stdin, and these two
  errors get one more try. After the change, the 8 calls worked.
- **Large repositories are slow.** With 3 cases at a time, most reviews and triages took 1–5 minutes.
  In posthog, n8n, infisical and twenty they took 15–40 minutes. The posthog triage took 38 minutes
  also when the agent answers came from the cache, so the time is in the evidence search and the
  known effects, not in the models.
- Cost: review $3.89 and triage $2.53 for 40 pull requests (~$0.16 for each), labels $7.82.

## Lessons

1. **Deterministic filters work better than better prompts.** The selection included "A design MUST state…" for code
   diffs until statements could narrow `Artifacts: spec`.
2. **Tasks need their own wording.** "Does the content contain…" fails for planned work.
   "will the work have to follow…" plus a code-level artifact filter raised task recall
   from 0.29 to 0.86.
3. **Indirection breaks Jev, as the documentation says.** A conflict checker put the whole corpus in
   one state and asked about `existing[i]`. It returned "conflict" for nearly every pair. One
   small state for each pair fixed it.
4. **A Choice splits the probability between true answers.** A pair that both conflicts with and
   weakens a rule scored 0.51 / 0.49 and passed. We sum the failing classes and add two
   absolute Nouls as the gate. This fixed it.
5. **Hierarchies drop recall without a warning.** The layered cascade looked equal on a small corpus
   and lost 11 points at ~540 statements.
6. **Give Jev the facts. Do not expect it to know libraries.** The timeout rule went from
   p 0.14 to 0.77 on one call when the state had the fact "downloads over the network".
7. **Measure on real data before you tune.** On written cases, triage removed 15 of 15 noise comments.
   On real pull requests it removed 10 of 55, and the developers acted on most of the "noise". The
   real data also showed two bugs that the written cases did not: the same-file evidence gap and the
   agent calls that failed under load.
8. **Mechanical rules need code, not a better question.** Jev cannot count functions without type
   hints. A 40-line `ast` check gives exact lines.

## Next steps

- Get human rulings on the real-PR sample (`eval/realpr/run.py review`, then `accept`). Then grow the
  set, and add pull requests of the organisation (with data-protection approval).
- Make a feedback loop: dismissed PR comments → labels → a threshold or an off switch for each rule.
  The real-PR eval shows that advisory noise comes from a few rules (JRFC-0010.1). Collect
  `health.json` across PRs to see the unknown rates and near misses over time.
- Profile the evidence search and the known effects on large repositories (15–40 minutes now), and
  move the blocking `git grep` calls out of the event loop.
- Grow `effects.yaml` from real repositories (an agent can draft entries from package docs;
  owners approve).
- Add more code checks for mechanical rules.
- Review the diffs that add a spec file as `spec` chunks, not as `diff` chunks.
- Split this repository into the organisation corpus and the tooling (the CI template already
  treats them as two checkouts).
