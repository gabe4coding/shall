# Authoring shall standards

A shall RFC is read by people and consumed by agents one statement at a time. Your job is
to produce a **draft** that a human domain owner can approve. You never decide that a
standard is in force.

## Hard rules

- New RFCs are created with `status: draft`. You MUST NOT set or change `status` to
  `approved` or `enforced`, and MUST NOT remove a statement's `Enforcement:` line to
  bypass a linter rule. Status changes are the owner's decision (JRFC-0001.4). If the
  user asks you to promote a standard, prepare the change and tell them the owner in
  the RFC front matter has to approve it in review.
- Never renumber a published statement id, and never reuse one. To remove a statement,
  delete its section and add its id to `retired: [...]` in the front matter (JRFC-0001.2).
  `shall lint --against <base index.json>` catches silent removals in CI.
- Never edit `corpus/index/*` by hand; it is generated by `shall build`.

## Workflow

1. **Check what exists.** Run `shall list` and read `corpus/index/catalog.md`. If the rule
   belongs in an existing RFC, add a statement there instead of creating a new RFC.
2. **Scaffold** a new RFC: `shall new --domain <domain> --title "<title>"` (prints the
   file path, picks the next free id). Domains are defined in `corpus/domains.yaml`; a new
   domain is a human decision, ask first.
3. **Write the statements** (format below).
4. **Lint**: `shall lint`. Fix every error. Treat warnings as work to do.
5. **Conflict check**: `shall conflicts <file> [--all-domains]` (or `shall conflicts --local`
   for all local rules of an app repo). It asks Jev, pair by pair, whether each new
   statement duplicates, weakens, conflicts with, or overlaps an existing one. Resolve every `FAIL` (duplicate, weakens, conflict): merge, reword, or cite the existing
   statement. Report `overlap` results to the user; some are intended refinements.
6. **Rebuild the index**: `shall build` (see the `shall-index` skill).
7. **Self-review**: `shall review <rfc file> --kind doc` checks the draft against
   JRFC-0001 (format and lifecycle).
8. Hand over: summarize the new statements, open questions, and the conflict results.
   Leave the PR to the user unless they ask you to open it.

## File format

```markdown
---
id: JRFC-0012                 # JRFC-NNNN, also the start of the file name
title: HTTP caching
status: draft                 # draft | approved | enforced | deprecated
domain: api                   # a key of corpus/domains.yaml
artifacts: [diff, code]       # which artifacts it can apply to: diff, code, spec, doc
languages: [any]              # or e.g. [typescript] — a deterministic prefilter
owner: platform
review_by: 2027-06-30
supersedes: []
summary: >
  One or two sentences: what the standard covers.
applies_when: >
  The concrete code or text it governs, written literally.
not_applies_when: >
  What looks close but is out of scope.
---

# JRFC-0012: HTTP caching

## Context
Why it exists. Links to incidents, ADRs, external references.

## Requirements

### JRFC-0012.1 Cache-Control on GET responses
GET handlers MUST set a `Cache-Control` header on successful responses.

- Applies when: the content adds or changes a GET handler that returns a response.
- Not applies when: the handler streams server-sent events.
- Artifacts: diff, code          # optional, narrower than the RFC's artifacts
- Enforcement: agent             # agent | linter | human
```

## Writing statements that work for agents

The selector (Jev) reads **literally**. It answers the words written, not the intent.

- **One requirement, one level.** Use exactly one level of UPPERCASE keywords per
  statement: MUST/MUST NOT/SHALL/REQUIRED, or SHOULD/SHOULD NOT/RECOMMENDED, or
  MAY/OPTIONAL. Two levels → two statements. Lowercase "must" has no normative meaning
  (RFC 8174); keywords in backticks are mentions, not uses.
- **Self-contained text.** The statement is shown alone, without the RFC around it. Do
  not write "as above" or "this service"; name the thing.
- **`Applies when:` names concrete things** a reader can point at in a diff or a doc:
  "a log call includes fields of a user", not "privacy-sensitive situations". This line
  becomes the Jev criterion, so vague text here causes missed or noisy reviews.
- **`Artifacts: spec`** for statements that only make sense for a design document
  ("a design MUST state …"). Without it, the statement is also asked about code diffs.
- **`Enforcement: linter`** when a linter can check it exactly (config flags, syntax,
  formatting). Agents skip those; point to the lint rule in the text (JRFC-0001.5).
- Prefer observable requirements over intentions: "MUST set a timeout" is checkable,
  "MUST be resilient" is not.

## Organisation corpus or local `.shall/`?

- A rule for **every** team goes to the organisation corpus (prefix `JRFC-`), owned by the
  domain owner in `corpus/domains.yaml`.
- A rule for **one repository** goes to that repo's `.shall/rfcs/` with the repo prefix
  (e.g. `BOOK-`). Create the layer once with
  `shall init --prefix BOOK --repo <org>/<corpus-repo> --ref <tag>`.
- Local rules may **add** requirements or **tighten** org rules. They must not repeat,
  relax or contradict an org rule: run `shall conflicts --local` and resolve every FAIL.
  If the user wants a local exception to an org rule, that is not a local rule: propose
  the change to the org RFC's owner instead. There are no waivers.
- Reuse org domains (`shall catalog`). Add a local domain in `.shall/domains.yaml` only for
  an area the org corpus does not cover; you cannot redefine an org domain.
- When the same local rule exists in several repos, suggest upstreaming it.

## Known effects (`effects.yaml`)

A rule about network calls, databases or processes is only selected when Jev can see that
the code does that. When a library hides it (`get_parser(lang)` downloads a grammar,
`db.Query` goes to the network), add an entry to `corpus/effects.yaml` (or
`.shall/effects.yaml`) instead of widening the rule's `Applies when:`:

```yaml
- id: go-database-sql
  module: database/sql                     # import spec, prefix match
  calls: [Open]                            # called through the import: sql.Open(...)
  methods: [Query, QueryRow, Exec]         # on a receiver from the module: db.Query(...)
  effect: runs a query on a remote database over the network
  owner: data-platform
```

Write `effect` as a literal clause ("<call> <effect>"). Prefer `calls` to `methods`: a method
name only matches when its receiver is traceably from the module. Entries are reviewed by
their owner like statements; `shall lint` checks the fields.

## Maintaining standards

- **Change a requirement's meaning** → add a new statement and retire the old id, so
  past review comments still point to the text they quoted.
- **Deprecate an RFC** → `status: deprecated` + `superseded_by: JRFC-NNNN` (owner approval).
- **`review_by` in the past** → `shall lint` warns; ask the owner whether the RFC is still
  right, then bump the date in the same change as any fix.
